## 0. 一句话结论

文档里的六个关键参数（`case_grade` / `courthouse_name` / `courthouse_province` / `decision_date_start` / `case_type` / `doc_type`）**全部实测生效**，可以放心照做。真正卡住落地的不是北大法宝的能力，而是**我们自己的输入缺口**：

1. `CaseContext` 里**没有任何「管辖法院」字段** → 顺位④的「上一级法院 / 本院」无源之水；
2. 现有散文解析器 **抽不到日期和裁判说理正文** → 「近五年」无法在客户端校验、「从新到旧」无法排序、注入 prompt 的类案只剩标题；
3. 参数键拼错时接口返回 **HTTP 200 + 校验错误正文**，现有 `_rpc_failed` 看不见 → 会被当成「检索到 0 个类案」。

前两条不解决，级联编排写得再漂亮，产出也是「看起来有顺位、实际上不可信」。

## 2. 问题清单（按处理顺序）

### P0-1　参数校验失败 = 静默 0 命中

拼错参数键时，接口**不走 HTTP 错误码**，而是返回 200 + 一段校验失败正文。现有链路：

- `_rpc_failed()` 只检查 `rpc_result["error"]` 键 → 这段正文不在 `error` 里，**看不见**；
- `_extract_items()` 在 `content[0].text` 里找不到编号列表 → 返回 `[]`；
- 上层 `_summary` 输出「检索到 0 个类案」。

结果与「真的没有类案」完全无法区分。文档第四节铺了六个过滤参数，每多一个参数就多一个拼错的机会——这条必须先修。

**修法**：`_rpc_failed` 增加对 `validation error / 1 validation error` 的识别，命中时返回 `status="error"` 并把正文前 200 字符附上；`_extract_items` 返回空时，调用方要区分「0 命中」与「解析失败」。

### P0-2　案号不是稳定主键

文档第五节要求「按案号去重」。但实测 `case_grade=典型案例` 返回的 5 条里，**4 条没有案号**——这类结果是「XX法院发布10起典型案例之八」式的汇编条目，`|` 后面直接是空的；而 `审理法院` 字段有时只到省级（如「湖北省」），不是法院全称。

后果：按案号去重会把典型案例几乎全部判重/丢弃，且失去这一高权威顺位的意义。

**修法**：去重主键三级回退 —— 案号 → `审理法院 + 标题前 30 字` → 标题全文。无案号的条目照常保留，但在展示层标注「无案号（典型案例汇编）」。

### P0-3　类案正文没进 prompt

`_parse_case_prose()` 只抽出 `title / court / ahao / case_type` 四个字段，**没有 summary**。下游 `search_for_*` 里 `it.get("ascertain", it.get("summary", ""))[:300]` 对散文条目恒为空。

也就是说：**现在注入模型 prompt 的类案只有「标题 + 法院 + 案号」，裁判说理一个字都没有**。而判定「这个类案像不像本案」的唯一依据就是裁判 reasoning。

**修法**：解析器扩字段，覆盖三套正文标签：

| 案例类型 | 正文标签 |
|---|---|
| 普通案例 | `本院查明` / `本院认为` |
| 典型案例 | `基本案情` / `裁判结果` / `典型意义` |
| 汇编/其他 | `裁判理由` |

同时抽出 `审结日期`、`案由`、`链接`（URL 已存在于返回文本，可用于报告超链）。

### P1-1　「近五年」现在是硬编码 `2020-01-01`

`search_for_financial()` 里写死 `decision_date_start="2020-01-01"`，按今天算是 **6 年**且逐年漂移。改为 `今天 − 5 年` 动态计算（`datetime.now().year - 5`）。

### P1-2　服务端不排序，需客户端兜

实测返回的日期序列是 `2009, 2014, 2013, 2008, 2019`，服务端**没有按审结日期排序**。文档第四节「按审结日期从新到旧排序」必须在客户端实现——依赖 P0-3 抽到的日期字段。

### P1-3　输入缺口：没有管辖法院 / 省份

这是最大的一条。`CaseContext` 现有字段里没有法院信息的任何位置：

- `legal_basis.py` 只有**描述性文本**（「一般由最高人民法院确定的基层人民法院管辖」、跃迁到「知识产权法院/中院」），不是可传参的法院全称；
- 前端立案表单不采集管辖法院；
- 唯一沾边的是企查查 `defendant_profile.metrics.facts.entity.region`（工商登记「所属地区」），那是**被告所在地**，不是管辖法院。

而文档的第六节「落地前置依赖」明确要求：法院层级推导表 + 省份→高院全称映射表。这两张表现在都不存在。

### P1-4　调用预算：不要每个节点各自级联

现有 4 个调用点会用 `search_case`：侵权认定、模拟法庭抗辩、判赔类案、判例价值。若各自跑满四顺位（每顺位 1–2 次调用），一次评估就是 **十几到二十几次 RPC**，每次 2–5 秒，串行起来足以让演示超时。

**建议**：把四顺位做成**一次统一的 `retrieve_similar_cases()`**（跑一次级联，产出 5–10 条带顺位标记的结果），各节点从结果里按用途取子集，而不是各跑各的。

### 实施中发现、文档未覆盖的问题：**高权威档会混入无关案由**

实跑「商标侵权 混淆可能性」+ `case_grade=指导性案例`，返回的 10 条里混进了环境污染、
植物新品种的指导案例。若严格照文档「凑够 5 个即停」，级联会在顺位①就停下，
结果反而拿不到顺位②③里大量真正对口的裁判——**检索增强变成噪声注入**
（本项目此前已在「著作权案子检索回商标法条」上栽过同类型跟头）。

处理办法（写在 `precedent_ladder.CAUSE_RELEVANCE_KEYWORDS`）：

- 每条案例按案由关键词打 `relevant` 标记（比对「案由」与「标题」）；
- **停止规则的计数口径从「原始条数」改为「相关条数」**，无关案例不计入达标数；
- 每次调用后立即检查是否达标（而非等整档跑完），2-A 够用时不再打 2-B，省一次 RPC；
- 无关案例**不丢弃**，只排到最后——报告仍可追溯，便于判断「是没有类案还是没检索到」；
- 未知案由显式抛错，不用别的案由的关键词去筛。

效果对比（同一查询，真实接口）：

| | 调用次数 | 命中 | 其中相关 | 排在首位 |
|---|---|---|---|---|
| 无相关性门 | 1 次 | 10 | — | 环境污染类指导案例被排在前 |
| 有相关性门 | 2 次 / 1.8s | 19 | 12 | 歌力思、同德福、小拇指等商标案 |
